# Account screens and password authentication

The default unauthenticated entry now follows the owner's reference: Email, Password, show/hide password, Forgot Password?, LOGIN, OR and Create an Account. The Uttara OMS theme and Google/email-code alternatives remain. Four static routes expose the full flow: /login/, /signup/, /forgot-password/ and /reset-password/.

Passwords are submitted directly through the existing Supabase client using signInWithPassword, signUp and updateUser. They are not sent to the OMS API, stored in profiles, logged or saved by application code. Signup requires matching passwords of at least eight characters and continues to require email confirmation. Existing Supabase Confirm sign up template already includes {{ .Token }}; signup verifies that token with type signup. Confirmation resends are throttled in the form; provider limits remain authoritative.

Forgot password sends resetPasswordForEmail with the exact same-origin /reset-password/ redirect. The existing Reset password email template includes {{ .ConfirmationURL }}. The destination handles the PKCE session before offering the new-password form; expired or missing sessions offer a fresh reset link. PKCE recovery links should be opened in the requesting browser. Root and other auth-entry listeners forward PASSWORD_RECOVERY to the dedicated reset page as a fallback. Successful password updates clear form values and sign out; failures never claim success. Enrolled authenticator users complete AAL2 verification on the recovery page before the password form is shown. Supabase reauthentication requirements still apply.

Provider configuration inspected on 2026-11-21: signup template uses an email code, recovery template uses the confirmation URL, and https://uttara-oms.pages.dev/reset-password/ was added as an exact redirect destination. No wildcard/origin, SMTP credential, confirmation, MFA, role or private-data policy change was made. Existing Google/code-only users can use their existing method; Forgot Password can establish a password where permitted by Supabase.

All successful sign-in methods enter the same /me and automatic basic-account registration checks. A password login does not grant a role, approve an application or bypass leader AAL2 enforcement. New basic users retain only their own profile/reports. Main administrator permission approval remains unchanged.

Verification includes mocked provider failures/successes, signup confirmation mismatch/code flow, reset destination/cooldown, missing recovery sessions, successful password update/sign-out, failed update handling and existing OTP tests. Real credential entry, email-code verification and final recovery password creation must be performed by the account owner in the live UI; the agent does not enter new credentials.
